# 系统架构图（architecture）

> 表达系统组成：分层、模块、部署拓扑、数据流。工具：**TikZ 为主**（复用 `flowchart-styles.tex` 双模式与 `pc sub`/`pc db` 样式）；Graphviz 仅在节点极多需要自动布局时备用。

## 图型清单

| 图型 | 适用 | 要点 |
|---|---|---|
| 分层架构图 | 逻辑分层（接入/服务/数据） | 层从上到下，依赖箭头只向下（或向内）；每层模块 ≤5 |
| 部署拓扑 | 物理节点、集群、网络 | 节点形状区分机器类型（服务器/数据库/网关）；冗余用 ×N 标注 |
| 数据流图（DFD） | 数据在模块间的加工路径 | 与控制流分开画；外部实体、加工、存储用不同形状 |
| C4 模型 | 由粗到细的多级架构叙事 | 先 Context → Container → Component，每级一张图，不混层 |

## 必守规范

1. **一张图只讲一个抽象层级**：不要把"用户浏览器"和"Redis 缓存策略"画进同一张。想讲多层，用 C4 分级多画几张。
2. **依赖方向一致**：箭头统一表达"调用"或"数据流向"，二选一并在图注声明；禁止箭头双向混用（双向依赖本身是坏味道，如实画出并标注）。
3. **形状语义统一**：矩形=服务、圆柱=存储、六边形=外部系统、虚线框=逻辑边界。全图/全套交付物一致。
4. **模块名极短 + 编号**：框内写"网关 (GW)"级别；技术栈版本放图注（"Nginx 1.25"），不塞进框。
5. 关键路径/核心模块用主题强调色，支撑模块灰色——读者 3 秒内找到主角。
6. 子图边界（subgraph/cluster）只表达**物理或组织边界**（VPC、团队、阶段），不表达"我觉得这些像一类"。
7. 外部系统必须与内部系统视觉区分（形状或灰度），防止误读为自家模块。

## 常见错误

- ❌ 万物皆矩形 + 万箭齐发（无形状语义、无依赖方向）
- ❌ 一张图塞下三层抽象（用户 → 微服务 → 数据库字段）
- ❌ 布局完全手摆导致连线交叉（交给 Graphviz dot 自动布局）
- ❌ 缓存、消息队列画成普通框（它们是数据平面的关键，用专门形状）
